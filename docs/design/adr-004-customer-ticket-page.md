# ADR-004：客户工单页 —— 互斥四桶状态模型 + 后端草稿 + 客户侧软删除

> 状态：**已采纳**（2026-08-16 拍板：D1 互斥四桶 / D2 草稿后端持久化 / D3 软删除 / D4 全部状态可删 / D5-D12 交互细节） · 关联：[ADR-003 实时消息](adr-realtime-websocket.md)、[ADR-002 SLA 双层配置](adr-sla-two-tier-config.md) · 设计说明：[customer-ticket-page-design.md](../product/customer-ticket-page-design.md)

## 1. 背景

CustomerWeb V3 服务台需要重新设计工单页：支持 待提交/进行中/已完成/待评价 四维筛选、客户侧删除与批量删除、新建时草稿续填提示、标题+描述必填。现状（已勘察）：前端列表仅「全部/待处理/进行中/已完成」三桶聚合（`ticket-lifecycle.ts`），无草稿、无删除；后端 `ticket` 表无 draft/is_deleted 字段，客户列表接口仅 status+limit，无任何删除/草稿端点。

## 2. 决策

1. **互斥四桶状态模型**：客户视角工单分为 待提交（=草稿，独立表 `ticket_draft`，非工单状态）/ 进行中（open, processing, waiting_customer）/ 待评价（resolved, closed 且满意度未评）/ 已完成（已评的 resolved/closed + withdrawn）。每单只落一桶，无重叠，杜绝「一单同时出现在两个 Tab」的认知混乱。
2. **草稿后端持久化**：新建 `ticket_draft` 表（每客户每业务域一稿，uk_draft_domain_customer），输入防抖自动保存；新建时存在草稿则弹「发现尚未提交的草稿，是否继续」。选后端而非 localStorage：草稿必须跨设备/跨会话可感知、后端可校验、客服侧未来可复用（如客服代填）。
3. **删除 = 客户侧软删除**：`ticket` 表加 `deleted_at`/`deleted_by`，客户列表过滤；客服端仍可见（历史完整性与审计）。不做硬删（审计断链、不可逆），不做双端隐藏（处理中工单在客服队列消失会破坏连续性）。
4. **全部状态可删**：草稿/进行中/待评价/已完成均允许客户删除，进行中及以后弹强确认。客户对自有数据的处置权优先，客服端保留可见兜底。
5. **交互形态**：全部+四桶 Tab（默认全部，全部不含草稿）、保留左侧类型栏、页首加四桶计数统计条（对齐 Figma v3 首页）、hover 复选框 + 批量操作条、删除不可恢复。

## 3. 被否决的替代方案

- **状态桶重叠**（待评价作为已完成子集）：两 Tab 同时出现同一单，筛选语义模糊，否决。
- **localStorage 草稿**：换设备/清缓存丢失、后端无感知，无法支撑「新建时提示草稿」，否决。
- **硬删除 / 双端隐藏软删**：前者审计断链不可逆，后者破坏客服处理中工单连续性，均否决。
- **仅草稿/仅已完成可删**：不满足「支持删除」的完整预期，客户对处理中工单的删除需求真实存在，否决。

## 4. 后果

- **有利**：客户侧数据自治理完整（草稿/删除/批量）；四桶语义清晰可扩展（未来加桶只需扩展映射函数）；软删保留客服端历史与审计链路；ticket_draft 独立表不污染工单编号序列。
- **代价**：需新增 6 个端点（draft CRUD×3 + 单删 + 批量删 + 列表扩展 evaluated 字段）；`ticket` 表迁移加 2 字段 + 1 索引；满意度评价后需联动刷新（待评价→已完成 的桶迁移依赖详情页评价动作后的列表刷新）。
- **边界**：客户列表保持前端全量过滤（不引入服务端分页，量变时再议）；客服端「客户已删除」标记为可选后续项，本期不实现。
