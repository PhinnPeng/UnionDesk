# Research: PRD 功能清单是否需细化到 CRUD 操作级

- **Query**: 是否有必要在 PRD 中增加功能清单图，且细致到列表 / 详情 / 新增 / 删除 / 更新等 CRUD 操作级？
- **Scope**: mixed（外部模板规范 + 仓库内部文档取证）
- **Date**: 2026-08-11

## Findings

### 1. PRD 模板对功能清单的粒度要求（`PRD指南.md`）

来源：`C:\Users\Administrator\.config\opencode\skills\prd-review-optimizer\template\PRD指南.md`（实际读取路径为 `C:\Users\Administrator\.skills-manager\skills\prd-review-optimizer\template\PRD指南.md`，内容一致）。

- **§4.2 功能清单图的定位**（原文）：「用穷举法列出每个模块下会发生的功能，**类似详细设计的目录**」——功能清单是索引（Index），不是细节载体。
- **M/F 编号体系**（原文）：「`M` 开头代表模块（Module）；`F` 开头代表功能（Feature）」——模板的编号体系只到 **Feature 级**，无 F 以下的子级（如 F1.1.1 操作级）示例。
- **功能清单的四个用途**（原文）：「1. 给团队全貌… 2. Tech Lead 根据功能清单分配任务… 3. 类似索引，保证任务不被遗漏 4. **测试团队根据功能清单准备 Test Case**」——面向 Test Case 准备的是「功能不遗漏」，而非操作细节。
- **操作级细节的归属**（原文，§五 详细设计）：「将交互图中**每个页面的逻辑一一对应**讲清楚」「详细设计要与功能清单、页面结构**一一呼应**」——操作/交互级逻辑的权威位置是**详细设计**章节，而非功能清单图。
- **自洽检验**（§4.3）：模板要求的是「功能清单 ↔ 页面结构 ↔ 详细设计」三层自洽，无操作级清单的第四层要求。
- **结论：模板不要求操作级（CRUD）粒度**。模板的功能清单到「功能」级止；CRUD 细节属于详细设计。

### 4. 权衡分析（证据导向）

**增加 CRUD 级功能清单图的收益**：
- 可追踪性：54 条 × 操作集合可直接支撑「验收/测试不遗漏」（模板用途 4：测试团队准备 Test Case）。
- 现状 gap：feature-list.md 操作级覆盖约 6 成且不系统（见 §2），补齐后消除「操作是否存在」的空白决策点（如 F3.1 删除、F1.4 取消工单）。

**代价**：
- PRD 膨胀：54 条 × 5 操作 ≈ 270 行（若并入 prd.md §4.2 表格，7 列 → 10+ 列，破坏「索引」定位，违背模板「类似详细设计的目录」定位）。
- **重复**：操作+校验细节已在 L6 backlog AC（精确到校验与权限码）与 inventory 备注（按操作拆行）存在；PRD 再加 = 第三份副本，三处维护漂移风险（feature-list.md 已出现「US-S3-01 状态」与 inventory 的偏差注释即先例）。
- 维护成本：每改一个操作需同步 prd + feature-list + backlog。

**行业惯例**：功能清单（Feature List）通常到**功能级**（模块 M / 功能 F 两级编号即模板上限）；CRUD 操作级属于**详细设计 / 测试用例 / 接口文档**粒度，而非功能清单图。

## 结论

1. **模板要求**：功能清单 = 「类似详细设计的目录」（索引），编号到 F 功能级为止；操作级细节归属**详细设计**章节；测试团队基于功能清单准备 Test Case 的用途靠「功能不遗漏」实现，不要求操作级展开。
2. **现有产出覆盖度**：prd.md §5 与 feature-list.md 功能说明列已覆盖约 6 成条目的主要操作（含列表/详情/新增/编辑/删除），但**不系统**：操作未按固定集合枚举、「CRUD」缩写与全列混用、客户端条目普遍缺操作枚举、删除/边界校验类决策点散落（缺例：F3.1 删除约束、F1.4 取消/撤回工单边界、F4.3 恢复/重置密码/无永久删除入口）。
3. **仓库既有操作级承载位置**：`docs/product/backlog-stories.md`（L6，AC 精确到操作+校验+权限码，迭代任务源）、`docs/product/implementation-inventory.md`（按操作拆行 + 备注列）；PRD 再加操作级 = 第三副本。
4. **明确建议**：**不必要在 prd.md 中新增 CRUD 级功能清单图**（违背模板索引定位、与 L6 AC / inventory 重复、270 行膨胀）。**部分必要**：若目标是「验收/测试可追踪」，最小方案是在 **feature-list.md**（现状操作信息载体）补一个**操作矩阵小节**，而非扩展现有 54 行表或改 prd.md。
5. **推荐最小改动形态**（若采纳，供主代理决策）：在 feature-list.md §5 后新增「## 7. 操作矩阵（按功能编号）」小节，每功能一行，列：`功能编号 | 列表 | 详情 | 新增 | 编辑 | 删除 | 其他操作 | 校验/边界（引用 FR/TR 或 Story AC）`，单元格填 `✔`（有）/`—`（无）/`部分`（受限）+ 简注；删除/边界决策点（如 F3.1 删除约束、F4.3 永久删除无入口）直接在矩阵单元格标注。预计 54 行 × 8 列，增量约 60–80 行，不破坏 prd.md §4.2 索引定位，且与 §5 详细设计、L6 AC 形成引用链。
